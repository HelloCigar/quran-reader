# Quran Reader — Implementation Plan

> Task type: greenfield
> Stack: AdonisJS + Inertia React
> Database: SQLite

## Summary

A public, read-only Quran reader. A domain service fetches the surah list and each surah (Uthmani Arabic and Saheeh International English) from Al Quran Cloud, using a typed client generated by Hey API from the provider's OpenAPI spec. It caches the results with `@adonisjs/cache`: memory L1 in front of a SQLite L2, 30-day TTL plus a grace period. Two pages, `/quran` and `/quran/:number`, render the list and the reading view. A dedicated 503 page shows the brief's "couldn't be loaded" message.

## Pre-implementation requirements

- `@adonisjs/cache` (v2.x). This change chose it as the cache. Install with `npm install @adonisjs/cache`, then run `node ace configure @adonisjs/cache` and select the **database** driver for L2. `cache.md` is already in the harness.
- `@hey-api/openapi-ts` (dev dependency, v0.99.x) generates the typed Al Quran Cloud client from the OpenAPI YAML. The fetch client is bundled into the generated output (the separate `@hey-api/client-fetch` package is deprecated), so nothing is added at runtime.
- `package.json` `imports` gets two aliases: `"#types/*": "./types/*.js"` and `"#integrations/*": "./app/integrations/*.js"`.
- `package.json` `scripts` gets `"openapi": "openapi-ts"`.

## Out of scope

- A dedicated Arabic Quran font, such as Amiri Quran or KFGQPC Uthmani. With system fonts, some Uthmani marks may render imperfectly on some devices. A font is a separate visual-polish change.

## Target shape

`SurahsController` (`index`, `show`) delegates to `QuranTextService`.

- The service wraps a Hey API–generated Al Quran Cloud client. It stores plain JSON domain shapes (`types/quran.ts`) in the `quran` cache namespace: memory L1, a SQLite `cache` table as L2, `ttl` 30 days, `grace` 30 days.
- The service guarantees complete text. Ayah 1's leading Bismillah is lifted into its own `bismillah` value for surahs 2–114 except 9, and a leading U+FEFF is stripped. Any failure surfaces as `QuranUnavailableException`, which renders `errors/quran_unavailable` with status 503.
- A custom route matcher limits `:number` to 1–114, so any other value falls through to the existing 404 page.
- `SurahTransformer` and `AyahTransformer` shape the props for `quran/index` and `quran/show`.
- The home page gets a "Read the Quran" button.

## Logical schema

Reads: migrations.md, schema-rules.md, cache.md

The only table is the cache's SQLite L2 store. The app has no Quran entities: surahs and ayahs live in the cache, not in app tables.

```dbml
// Owned by @adonisjs/cache (BentoCache database driver), created by an app migration
Table cache {
  key varchar(255) [pk, note: 'BentoCache key, prefixed by the "quran" namespace']
  value text [note: 'serialized cache entry (JSON + BentoCache metadata)']
  expires_at timestamp [null, note: 'null = no expiry']
}
```

Things the DBML can't express:

- **Who owns the shape.** The column shape belongs to BentoCache's database driver. Before writing the migration, build must check it against `node_modules/bentocache` and use whatever the driver expects, not this sketch.
- **Who creates the table.** A Lucid migration creates it, and the driver is set to `autoCreateTable: false`. migrations.md forbids schema changes made outside migrations on a Lucid-managed database.
- **Schema generation.** The table is added to `schemaGeneration.excludeTables` in `config/database.ts`, so `database/schema.ts` gets no class for it. Nothing reads it through Lucid.
- **What's stored.** The cache holds plain JSON domain shapes, never models (cache.md).
- **The table name.** It is `cache`, the name the `@adonisjs/cache` configure command scaffolded (amended at build, 2026-11-13; the driver gets `tableName: 'cache'`). Every cache namespace shares it, and the `quran` namespace prefixes the keys.

## Service design

Reads: services.md, controllers.md, cache.md

`node ace make:service quran_text`

- `app/services/quran_text_service.ts`: `QuranTextService`. It isn't named after the vendor, so the text source can change without renaming it.
  - `listSurahs(): Promise<SurahSummary[]>` returns all 114 surahs in order.
    - It uses `quranCache.getOrSet({ key: 'surahs', ttl: '30 days', grace: '30 days', graceBackoff: '5 minutes', factory })`.
    - The factory calls the generated client's surah list operation (`GET /surah`) and maps each row into `SurahSummary`.
  - `readSurah(number: number): Promise<Surah>` returns one surah, complete.
    - It uses `quranCache.getOrSet({ key: \`surah:${number}\`, ttl, grace, graceBackoff })` with the same values.
    - The factory calls the generated client's surah-by-editions operation with `quran-uthmani,en.sahih`. It pairs the two editions ayah by ayah on `numberInSurah`.
    - It strips a leading U+FEFF from every Arabic ayah.
    - **Bismillah:** for surahs 2–114 except 9, if ayah 1's Arabic **starts with the exact Uthmani Bismillah plus a space**, that prefix is removed. `bismillah` is then set to the Bismillah text; otherwise it's `null`. The constant is the Bismillah text from `quran-uthmani` 1:1 with the U+FEFF removed. It stays private to the module, since services.md allows a service file to export only the class.
    - Surah 1 keeps the Bismillah as ayah 1, with `bismillah: null`. Surah 9 has `bismillah: null`.
  - **Both methods are all-or-nothing.** The factory throws `QuranUnavailableException` in any of these cases:
    - a network error or timeout;
    - an HTTP status other than 2xx;
    - a body `code` other than 200;
    - a number of editions other than 2;
    - a list with other than 114 rows;
    - an ayah count that differs from `numberOfAyahs` or between the two editions.

    A factory that throws is never cached. While a stale copy is still inside the grace period, BentoCache returns it instead (cache.md).

  - Each method wraps its `getOrSet` call. Any error it throws, including BentoCache wrapping a factory error, is rethrown as `QuranUnavailableException` with the original as `cause`.
  - **Outbound timeout:** each client call is cut off after 10 s (`AbortSignal.timeout`), so a stuck upstream can't hold a request open forever.
  - **The client is a module-level import**, not something injected. It's a plain stateless function client with nothing for the container to resolve.
  - **Does NOT:**
    - touch the HTTP context, render, or redirect;
    - format ayah references like "2:255" (that's the transformer's job);
    - work out the previous and next surah (the controller does that);
    - check surah numbers (the route matcher guarantees 1–114).

Supporting files:

- **Cache namespace:** `start/cache.ts` exports `quranCache = cache.namespace('quran')`. This is the only place the namespace is declared (cache.md).
- **Domain types:** `types/quran.ts` holds
  - `SurahSummary { number: number; arabicName: string; name: string; meaning: string; revelation: 'Meccan' | 'Medinan'; ayahCount: number }`
  - `Ayah { number: number; arabic: string; english: string }`
  - `Surah = SurahSummary & { bismillah: string | null; ayahs: Ayah[] }`
- **The OpenAPI spec:** a committed, pinned copy at `resources/openapi/alquran_cloud.yaml`, downloaded from `https://api.alquran.cloud/v1/documentation/openapi/yaml`.
- **Hey API config:** `openapi-ts.config.ts` at the project root.
  - Input is the YAML above; output is `app/integrations/alquran_cloud/`.
  - It uses the `@hey-api/client-fetch` plugin with `baseUrl: 'https://api.alquran.cloud/v1'`.
  - Generated imports use `.js` extensions to match the ESM `#` aliases. Build checks the exact option name against the installed version.
- **Generated client:** `app/integrations/alquran_cloud/**` is generated and committed, and never edited by hand.
  - It's regenerated with a new `npm run openapi` script (`openapi-ts`).
  - It gets the alias `"#integrations/*": "./app/integrations/*.js"` in `package.json` `imports`.
  - It's added to the lint and format ignore lists.

## Validation

Reads: validation.md, request.md, routing.md

### Input validation

No validator file. Neither action reads a body, a query string or headers. The only input is the `:number` route parameter, and validation.md and request.md say route parameters are constrained by route matchers, not by `validateUsing`. No `node ace make:validator`.

### Business rules

- **Surah number is a whole number from 1 to 114.** This is owned by a **route matcher** on `:number` (written out in Routes).
  - The matcher pattern is `^(?:[1-9]|[1-9]\d|10\d|11[0-4])$`, with a cast to `Number`.
  - The built-in `router.matchers.number()` can't limit the range, which routing.md accepts as a reason for a custom matcher.
  - If the matcher fails ("0", "115", "abc", "02"), no route matches. The framework's 404 then renders `errors/not_found` through the existing `statusPages`, so no controller code is needed.
  - In development, `renderStatusPages` is off, so the debug 404 page appears there instead. That's expected.
- **The upstream response must be complete before anything is shown.** This is owned by the service method (see Service design).

## Authorization + segregation

Reads: authentication.md, authorization.md

- **Policy or rule classes:** none. Reading is open to everyone (brief: "Reading never requires an account"). Neither action has a permission key or a check that depends on runtime data.
- **Permission and role keys:** none. `@adonisjs/bouncer` isn't installed, and this change doesn't need it.
- **Route protection:** both `surahs.*` routes are outside the `middleware.auth()` and `middleware.guest()` groups.
  - The global router stack already runs `silent_auth_middleware`, so a signed-in visitor still gets `props.user` and the nav (`MarketingLayout` reads `props.user`).
  - Guests are never redirected.
- **Query segregation:** none. There's no per-user data, and every visitor sees the same text and the same cache entries. The cache keys hold no user identity, so cache.md's rule against caching authenticated request state holds.

## Controllers

Reads: controllers.md, http-context.md, request.md, middleware.md, exception-handling.md

I skipped model-relationships.md because this change has no models or relationships.

`node ace make:controller surahs`

- `app/controllers/surahs_controller.ts` (new).
  - `index`: calls `QuranTextService.listSurahs()`, passes the result through `SurahTransformer`, and renders `quran/index`.
    - Props: `{ surahs: SurahTransformer.transform(surahs) }`.
    - It delegates to the domain service because the work is a cached call to a third-party API.
  - `show`: calls `QuranTextService.readSurah()` and `.listSurahs()`, passes the results through `SurahTransformer` (the `forReading` variant for the surah) and `AyahTransformer`, and renders `quran/show`.
    - `params.number` is already a `number`: the route matcher casts it (http-context.md says params are strings unless a matcher casts them). There's no range check in the controller; the route matcher covers it.
    - The two service calls run concurrently with `Promise.all([readSurah(number), listSurahs()])`. Once cached, both come from the cache.
    - `previous = surahs[number - 2] ?? null` and `next = surahs[number] ?? null`. Surah 1 has no previous and surah 114 has no next.
    - Props:
      - `surah: SurahTransformer.transform(surah).useVariant('forReading')`
      - `bismillah: surah.bismillah`, a plain `string | null`
      - `ayahs: AyahTransformer.transform(surah.ayahs, surah.number)`
      - `previous` and `next`: `SurahTransformer.transform(x)` or `null`
      - Each transformer wraps a top-level prop value (controllers.md).
    - It delegates to the domain service because the work is a cached call to a third-party API.
  - Neither action uses try/catch. `QuranUnavailableException` handles itself (exception-handling.md).
- DI: class-level `@inject()` with the constructor taking `QuranTextService`, since both actions use it (controllers.md).

`node ace make:exception QuranUnavailable`

- `app/exceptions/quran_unavailable_exception.ts` (new): `QuranUnavailableException extends Exception`.
  - `static status = 503`, `static code = 'E_QURAN_UNAVAILABLE'`.
  - The default message is the brief's wording: "The Quran text couldn't be loaded right now. Please try again in a moment."
  - `handle(_error, ctx)` sets `ctx.response.status(503)` and returns `ctx.inertia.render('errors/quran_unavailable', { message: this.message })`. This is the dedicated-error-page pattern from exception-handling.md, and a custom `handle()` overrides the generic 500–599 status page.
  - `report(_error, ctx)` writes `ctx.logger.warn({ err: this.cause }, 'Quran text unavailable')`, so the upstream failure gets logged without an error-level alert.

## Response layer

Reads: transformers.md, response.md, session.md, exception-handling.md

`node ace make:transformer surah`

- `app/transformers/surah_transformer.ts`: `SurahTransformer extends BaseTransformer<SurahSummary>`. `Surah` is a `SurahSummary`, so the same transformer accepts both.
  - Fields that need transforming in `toObject()` (list rows and previous/next links):
    - `ayahCount: { raw: number, formatted: string }`. `formatted` is `"<n> ayahs"`. The shortest surahs have 3 ayahs, so it's always plural. Values are formatted on the backend (transformers.md).
  - Pass-through fields in `toObject()`: `number`, `name`, `meaning`.
  - Variant `forReading()` (the surah heading) spreads `await this.toObject()` and adds the pass-through fields `arabicName` and `revelation`.
  - No relationships to preload. It needs no runtime context, and `toObject()` is synchronous.

`node ace make:transformer ayah`

- `app/transformers/ayah_transformer.ts`: `AyahTransformer extends BaseTransformer<Ayah>`.
  - Its constructor takes `(resource: Ayah, surahNumber: number)`, the per-request extra pattern from transformers.md. The controller passes it as the second argument to `AyahTransformer.transform(surah.ayahs, surah.number)`.
  - Field that needs transforming: `reference: string`, which is `"<surahNumber>:<number>"`, e.g. `"2:255"`.
  - Pass-through fields: `number`, `arabic`, `english`. `arabic` goes out exactly as the service returns it, never trimmed or normalized.
  - No relationships to preload. It needs no runtime context, and `toObject()` is synchronous.

- Error page props: `errors/quran_unavailable` receives `{ message: string }` directly from the exception. It's a plain value, so no transformer.
- The page title uses each page's `<Head title>`, like the existing pages. There's no third-argument HTML metadata.

## Routes

Reads: routing.md

```diff title="start/routes.ts"
 router.on('/').renderInertia('marketing/home', {}).as('home')
+
+router.get('/quran', [controllers.Surahs, 'index'])
+router
+  .get('/quran/:number', [controllers.Surahs, 'show'])
+  .where('number', {
+    match: /^(?:[1-9]|[1-9]\d|10\d|11[0-4])$/,
+    cast: (value) => Number(value),
+  })
```

- The static `/quran` route is registered before the dynamic `/quran/:number` route (routing.md ordering).
- There's no `.as(...)`, so the routes keep their auto names `surahs.index` and `surahs.show`.
- No route-level middleware. Both routes are public (see Authorization + segregation).
- The custom matcher is there because `router.matchers.number()` can't limit the range (see Validation).
- After the controller exists, run `node ace codegen` if the dev server isn't running, so `controllers.Surahs` resolves.

Verify route names with `node ace list:routes`.

## Test coverage gap

**Existing coverage:**

- `tests/browser/navigation.spec.ts` covers the home page and its links into sign-up and login. It must keep passing after the home page gets its new button.
- Nothing covers the Quran reader.

**New browser tests**, in `tests/browser/quran/`, one file per flow:

- **Reaching the reader.** Home → "Read the Quran" → the list of 114.
- **The list.** Row format, and opening a surah.
- **Reading a surah.** Heading and Bismillah rules for surahs 1, 2 and 9; the Arabic and English text with "2:255"-style references; the credit line.

- **Shareable addresses.** A 404 for 0, 115 and "abc".
